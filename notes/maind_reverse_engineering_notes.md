# Yandex Station Lite — заметки по исследованию устройства

> Сводка находок из изучения прошивки, процессов и обработки кнопок. Документ составлен по наблюдениям и декомпиляции на текущий момент. Он намеренно отделяет подтверждённые факты от рабочих гипотез и открытых вопросов.

## 1. Краткая сводка

- Устройство работает на системе семейства **Buildroot**, в окружении есть BusyBox и `init`-скрипты.
- Главный исполняемый файл платформы — `maind`. Он запускается в нескольких экземплярах с разными ролями (`--platformd`, `--mediad`, `--telemetry`, `--fluent-bitd`, `--updatesd`, `--updater_gateway`). Это не означает, что все экземпляры выполняют одну и ту же функцию.
- За обработку кнопок в исследованном сценарии отвечает экземпляр **`maind --platformd`**. Процесс держит открытыми `/dev/input/event0`–`event3`.
- В `maind` найдены строки и символы, связанные с `DevInputButtons`, `ButtonsHandler`, `button_event_resolver`, `startConversation`, `stopConversation`, `handlePlayPause`, `MUTE_KEY` и `AliceCapabilityProxy::toggleConversation`.
- Установлена логическая цепочка обработки кнопки, но **точный физический Linux key code кнопки активации пока не установлен окончательно**.
- Убийство `maind` может привести к остановке нескольких подсистем или автоматическому перезапуску процесса через launcher. Для экспериментов предпочтительнее сначала выяснить роль конкретного PID.

## 3. Загрузка системы и запуск Quasar

По изученным заметкам, общая цепочка загрузки выглядит так:

```text
BusyBox init
  └─ /etc/inittab
      └─ /etc/init.d/rcS
          └─ запуск /etc/init.d/S??* по порядку
              └─ /etc/init.d/S99quasar
                  └─ /system/vendor/quasar/onboot.sh start
                      └─ запуск Quasar через run.sh
                          └─ quasar_launcher2 /system/vendor/quasar/launch.json
                              └─ несколько экземпляров maind с разными ролями
```

Это схема, собранная по найденным скриптам и описанию окружения. Перед внесением постоянных изменений стоит перепроверить фактическое содержимое скриптов на текущей прошивке.

### Роли `maind`

При просмотре процессов встречались роли:

| Аргумент запуска | Предполагаемая область ответственности | Уверенность / комментарий |
|---|---|---|
| `--platformd` | Платформенная логика, в том числе кнопки | Подтверждается открытыми input-устройствами и найденным кодом |
| `--mediad` | Медиаплеер и аудиофункции | Соответствует найденной архитектуре, но не вся связь проверена экспериментально |
| `--telemetry` | Телеметрия | Название роли указывает на назначение |
| `--fluent-bitd` | Сбор/пересылка логов | Название роли указывает на назначение |
| `--updatesd` | Обновления | Название роли указывает на назначение |
| `--updater_gateway` | Шлюз/сервис обновления | Название роли указывает на назначение |

**Важно:** `killall maind` завершает все процессы с именем `maind`, а не только `--platformd`. Launcher может их автоматически запустить заново.

### Пути и строки, представляющие интерес

В бинарнике/на файловой системе встречались:

```text
/system/vendor/quasar/onboot.sh
/system/vendor/quasar/launch.json
/system/vendor/quasar/quasar.cfg
/etc/inittab
/etc/init.d/rcS
/etc/init.d/S99quasar
/data/quasar/daemons_logs/

```

Также были строки/пути:

```text
/data/quasar/devices.json
/data/quasar/activate_adb_quasmodrom
/data/quasar/activate_network_adb
```

`/data/quasar/devices.json` может содержать ключи, токены и другие секреты. **Не включать содержимое этого файла в публичные логи, репозиторий или этот документ.** Пути активации ADB записаны как найденные имена; не следует считать их назначение полностью установленным без проверки содержимого и контекста использования.

## 4. Подсистема кнопок: установленная цепочка

Рабочая модель обработки кнопок:

```text
Linux input device (/dev/input/event*)
        ↓
DevInputButtons
        ↓
сопоставление input_event.code с внутренним ID кнопки
        ↓
ButtonsHandler
        ↓
зарегистрированное действие для логического ID
        ↓
startConversation / stopConversation / другие обработчики
        ↓
дальнейшая логика платформы и Alice
```

Из `ps` и `/proc`:

- PID `1159` был процессом `maind --platformd` в момент проверки.
- Он держал открытыми `/dev/input/event0`, `/dev/input/event1`, `/dev/input/event2`, `/dev/input/event3`.
- По данным `getevent`/`/proc` и именам устройств:

| Узел | Имя/тип, обнаруженный при исследовании |
|---|---|
| `/dev/input/event0` | `gpio_keypad` |
| `/dev/input/event1` | акселерометр (`accel`) |
| `/dev/input/event2` | `input_btrcu` |
| `/dev/input/event3` | `adc_keypad` |

Сопоставление `/dev/input/event*` с конкретными физическими кнопками и их кодами всё ещё требует точного подтверждения.

### Строки и имена в бинарнике

В `maind` найдены, среди прочего:

```text
yandex_io/modules/buttons/dev_input/dev_input_buttons.cpp
builtin_buttons_capability.cpp
button_event_resolver.cpp
Start listening ButtonCapabilityCondition
ButtonActionLocked
MUTE_KEY
mute_key
onButtonPressed
onButtonReleased
onDoubleClickAction
Starting conversation
NAlice.TAliceCapability.TStartDataInputDirective
NAlice.TSpeechSession
YandexIO::AliceCapabilityProxy::toggleConversation(...)
```

Эти строки хорошо согласуются с найденной цепочкой обработки событий, но сама по себе строка не доказывает, что функция вызывается в определённом пользовательском сценарии.

## 5. Логические ID кнопок

В `FUN_009e3b18` найдена обработка конфигурации `buttons`, где строковые имена сопоставляются с внутренними ID:

| Имя в конфигурации | Внутренний ID |
|---|---:|
| `ACTIVATE` | `0` |
| `VOLUME_UP` | `1` |
| `VOLUME_DOWN` | `2` |
| `MUTE_KEY` | `5` |
| `MUTE_STATE` | `6` |
| `TOUCH` | `10` |

Эта функция также работает с параметрами `togglePressedThreshold` и `nextPressThreshold`. По текущему анализу, это относится к настройкам распознавания/таймингов нажатий, **а не к назначению функций кнопкам**.

Ключевое различие:

- Linux `input_event.code` — низкоуровневый код input-события.
- `ACTIVATE = 0` — внутренний логический ID в приложении.
- Физическая кнопка → Linux code → логический ID — это разные уровни отображения.

## 6. Инициализация кнопок в `maind`

### `FUN_009df930` — функция, условно названная `initButtons`

Указатель Thumb: `0x009df931`.

Функция регистрирует действия и создаёт источники ввода. В начале создаётся запись, связанная с узлом `gpio_keypad`:

```c
memcpy(&local_158, &DAT_003ab5a8, 0x38);
FUN_009e05c4(local_80, &local_158, 7, auStack_5c);

FUN_0055c160(auStack_3c, "gpio_keypad");
FUN_009e10e2(&local_158, auStack_3c, 0xe, 5);
FUN_009e04a2(auStack_5c, &local_158, 1);
FUN_009e045c(local_68, local_80, auStack_5c);
FUN_009e04c4(auStack_48, local_68);
FUN_00603010(&local_30, auStack_48);
```

При вызове `FUN_009e10e2` передаются `"gpio_keypad"`, `14` (`0x0e`) и `5`. По декомпиляции создаётся запись с числовыми полями, но **семантика этих двух чисел пока не доказана полностью**. Не следует автоматически трактовать `5` как Linux key code или как логический ID без проверки структуры.

Затем собираются данные для громкости:

```c
local_158 = 0x100000000;
local_150 = 0x800000002;
local_148 = 0x900000005;
FUN_008e4314(local_68, &local_158, 6, local_80);

FUN_0055c160((int)&local_158 + 4, "volume_up");
FUN_0055c160((int)&local_148 + 4, "volume_down");
FUN_009e085e(auStack_5c, &local_158, 2);
```

По именам видно, что создаются записи для `volume_up` и `volume_down`. Из-за упаковки полей в агрегаты и отсутствия символов отдельные числовые значения требуют дальнейшего анализа перед изменением.

Функция также читает конфигурацию `buttonsSettings`:

```c
uVar2 = (**(code **)(*(int *)*param_6 + 0x24))();
uVar2 = FUN_005f0852(uVar2, "maind", 5);
FUN_005da1b4(local_80, 0);
FUN_005d5726(local_80, uVar2, "buttonsSettings", 0xf, &local_158);
...
FUN_009e0508(param_1, ..., &local_30, local_68, ..., &local_158, ...);
```

То есть настройки кнопок извлекаются из конфигурации секции `maind`, ключа `buttonsSettings`.

### Регистрация действия `ACTIVATE`

Для логического ID `0` в одном из путей формируется набор callback-функций, куда входят:

```c
local_e8 = (code *)0x9fe361;
local_d8 = (code *)0x9fdcbd;  // startConversation
local_f8[0] = (code *)0x9fd225; // stopConversation
...
FUN_009e058a(auStack_1ac, &local_158, 9);
ButtonsHandler_registerClickPressedAction(uVar5, 0, auStack_1ac);
```

В альтернативной ветке, зависящей от `param_18 & 1`, вызывается:

```c
ButtonsHandler_registerClickAction(uVar5, 0, auStack_1a0, 1);
```

Это указывает, что действия для `ACTIVATE` регистрируются через `ButtonsHandler`; точный выбор регистратора зависит от флага/режима, который ещё нужно проследить до источника.

Другие найденные регистрации:

- ID `1` связан с callback по адресу `0x009fe2f9`, предположительно с обработчиком play/pause.
- Встречаются регистрации для других ID, включая mute/touch.
- Адреса в этой таблице — адреса из текущей Ghidra-базы, а не стабильные символы API.

## 7. Что делает `DevInputButtons`

### Конструктор и структура

- `FUN_009e12ac` соответствует конструктору `YandexIO::DevInputButtons` по RTTI.
- Размер объекта, используемый в одном из путей создания, — `0x90` байт.
- `FUN_009e045c` создаёт объект и передаёт ему список имён устройств и записи кнопок.
- `FUN_009e14b6` обходит `/dev/input`, собирает подходящие устройства, копирует записи кнопок и конструирует `DevInputButtons` с именами устройств и таблицей соответствий.
- `FUN_009e1164` сопоставляет сконфигурированные имена с путями устройств в `/dev/input`; при отсутствии узла есть строка лога `DevInputButtons.NodeNotFound`.
- `FUN_009e147e` копирует массив записей размером `0x18` (24) байта каждая.
- `FUN_009e1456` и `FUN_009e0636` участвуют в построении map/записей. В `FUN_009e0636` берутся два 32-битных поля с offset `+0x10` исходной записи и сохраняются в поля `+0x10` и `+0x14` новой записи. Вероятная интерпретация — входной код и внутренний ID кнопки, но её желательно подтвердить по месту использования.

### Vtable `DevInputButtons`

Vtable обнаружена по адресу `0x0118d43c`:

| Смещение | Адрес функции / метка | Что известно |
|---:|---|---|
| `+0x00` | `0x009e162d` | деструктор |
| `+0x04` | `0x009e1689` | thunk/деструктор |
| `+0x08` | `0x009e1699` | `FUN_009e1698` — обработка/опрос событий |
| `+0x0c` | `0x009e153b` | `LAB_009e153a`, назначение не подтверждено |
| `+0x10` | `0x009e1605` | `FUN_009e1604`, назначение требует проверки |
| `+0x14` | `0x00567b35` | назначение не подтверждено |
| `+0x18` | `0x009e14ad` | `LAB_009e14ac`, участвует в инициализации/обслуживании |

### Опрос input-устройств: `FUN_009e1698`

Эта функция похожа на `pollButtonEvents`:

- открывает сконфигурированные input-узлы;
- запрашивает версию input API через `EVIOCGVERSION` (`0x80044501`);
- запрашивает идентификатор устройства через `EVIOCGID` (`0x80084502`);
- читает имя устройства;
- запрашивает bitmap поддерживаемых кодов клавиш;
- использует `poll` и читает структуры input-событий;
- маршрутизирует события по типам. В текущей декомпиляции ветви для `type == 4` ведут к `FUN_009e268a`, для `type == 5` или `type == 1` — к `FUN_009e26b0`, а `type == 3` — к `FUN_009e2854`.

Точные названия типов Linux input в комментариях к этим ветвям лучше подтверждать по константам из исходников/заголовков Linux, а не только по номерам из декомпилятора.

### Сопоставление события с внутренней кнопкой: `FUN_009e26b0`

Важный фрагмент декомпиляции:

```c
iVar3 = FUN_009e2fae(param_1 + 0x2c, (int)param_2 + 10);
if (param_1 + 0x30 != iVar3) {
    // timestamp извлекается из timeval
    if (param_2[3] == 0) {
        FUN_009e3050(..., *(undefined4 *)(iVar3 + 0x14), timestamp, 1);
        callback(..., buttonId, 2, ...); // release
    } else if (param_2[3] == 1) {
        FUN_009e2fe4(..., *(undefined4 *)(iVar3 + 0x14), timestamp, 1);
        callback(..., buttonId, 0, ...); // press
    }
    // значение 2 (repeat) не обрабатывается этим фрагментом
}
```

Что можно заключить:

1. Код события извлекается из структуры `input_event` по offset `+10` байт в декомпилированной раскладке.
2. Через `FUN_009e2fae` ищется соответствующая запись в таблице.
3. Значение из найденной записи по смещению `+0x14` передаётся как внутренний ID кнопки.
4. Значение `0` в поле события обрабатывается как отпускание, `1` — как нажатие; значение `2` (repeat) здесь не проходит в эти ветви.

**Следующая важная задача:** найти точные значения записей таблицы Linux key code → logical button ID и подтвердить, какой код отправляет физическая кнопка активации.

## 8. Функции обработки действий

### `startConversation` — `FUN_009fdcbc`

Thumb-адрес: `0x009fdcbd`.

По декомпиляции:

- проверяется поле/состояние по `param_1[0x18]` и результат `FUN_00a10224()`;
- в одном пути логируется `Starting conversation` и вызываются виртуальные методы, связанные с началом разговора;
- в другом пути логируется `Start recording` и вызывается `FUN_00a103a8(param_1[0x18])`.

Не следует упрощать эту функцию до «всегда включает микрофон»: ветка зависит от состояния объекта и дополнительных проверок.

### `stopConversation` — `FUN_009fd224`

Thumb-адрес: `0x009fd225`.

Найденные признаки:

- пишет в лог `Stop conversation` и/или `handleStopConversation`;
- проверяет состояние;
- вызывает `FUN_009fe8fa(param_1[2])`;
- затем вызывает виртуальные методы остановки либо `FUN_00a10518(param_1[0x18])`.

Точная семантика отдельных состояний нуждается в дальнейшем трассировании.

### Play/pause — `FUN_009fd2f8`

В Ghidra это функция около `0x009fd2f8` (Thumb-переход может указывать на `0x009fd2f9`). В строках, связанных с обработчиками кнопок, она соотносится с `handlePlayPause`.

По анализу, она:

- может блокировать действие при открытой панели управления устройством или режиме deep standby;
- переключает состояние воспроизведения;
- может отправлять события `player_continue` / `player_pause`;
- содержит путь onboarding, когда устройство ещё не настроено.

### Блокировка действий

`FUN_009fe360` проверяет флаг по смещению `param_1 + 0x74` и логирует `ButtonActionLocked` с причиной `deepStandByEnabled`.

Это означает, что отсутствие реакции кнопки не обязательно свидетельствует о неверной регистрации: действие может быть заблокировано состоянием устройства.

## 9. `ButtonsHandler` и callback-обёртки

- `FUN_009e49b8` соответствует `ButtonsHandler_registerClickPressedAction`.
- Для логического ID кнопки и вектора callback-функций она передаёт действия дальше через виртуальные методы по смещениям vtable `+0x0c` или `+0x10`.
- `FUN_009e058a` формирует вектор элементов по 16 байт:

```c
undefined4 *FUN_009e058a(undefined4 *param_1, int param_2, int param_3) {
    *param_1 = 0;
    param_1[1] = 0;
    param_1[2] = 0;
    FUN_009e0ad2(param_1, param_2, param_2 + param_3 * 0x10, param_3);
    return param_1;
}
```

- По устройству кода элементы, вероятно, являются объектами `std::function` или эквивалентными 16-байтными объектами обратного вызова. Это вывод по структуре и использованию, а не восстановленная исходная декларация типов.
- `FUN_009e0ad2` — вспомогательная функция сборки/копирования вектора, в том числе с вызовами `FUN_00910cb6` и `FUN_009e0b12`.
- `FUN_009e3fb8` вызывает `FUN_00924c08()` и выставляет байт по `+0xC` в `1`.
- `FUN_009e75f8` выделяет объект размером `0x20`, задаёт два поля (`&LAB_009e766a+1` и `&DAT_0118d790`) и вызывает `FUN_009e75d0`.
- `FUN_009e75d0` перемещает/копирует поля другого объекта; `FUN_00560fa8` перемещает вложенный объект из трёх слов и обнуляет источник. Это похоже на упаковку/перемещение callback-объектов, а не на бизнес-логику действия.
- `FUN_009e4b7c` — `ButtonsHandler::registerSwipePressedAction`, судя по встроенной mangled-строке.
- `FUN_009e4158` — `ButtonsHandler::setupVolumeUpLongPressButtonHandler`.
- `FUN_009e3fc4` — `ButtonsHandler::setupVolumeDownButtonHandler`.

Практический вывод: не стоит начинать патч с `FUN_009e058a`, `FUN_009e0ad2` или перемещающих обёрток. Для изменения поведения нужно найти место, где регистрируется конкретный callback, либо сам обработчик, если требуется поменять реакцию на событие.

## 10. Сетевые эксперименты вокруг устройства

Отдельно исследовалась маршрутизация запросов устройства через машину-посредник с помощью OpenWrt/nftables и MITM-прокси. Это независимая часть исследования, не связанная напрямую с декомпиляцией `maind`.

В качестве примера использовалось правило перенаправления TCP-трафика от клиента `192.168.10.174` на компьютер `192.168.10.163:8080`:

```sh
nft add rule inet fw4 dstnat_lan ip saddr 192.168.10.174 meta l4proto tcp dnat to 192.168.10.163:8080
```

Перед применением следует проверить, что в текущей конфигурации действительно существует цепочка `inet fw4 dstnat_lan`, а также что правила не конфликтуют с текущими настройками firewall. Для HTTPS обычный DNAT на порт HTTP-прокси сам по себе не обеспечивает корректный TLS MITM: нужны поддержка соответствующего режима прокси, доверие CA на клиенте и понимание поведения приложения. В предыдущих экспериментах также проверялись Tinyproxy и `redsocks`; их конфигурация не является частью подтверждённой цепочки кнопок.

**Важное ограничение:** перенаправление/перехват следует использовать только в своей сети и на собственных устройствах либо при явном разрешении владельца. Не публикуйте извлечённые токены, приватные ключи, сертификаты или содержимое файлов с секретами.

## 11. Полезные диагностические команды

Команды ниже рассчитаны на BusyBox-подобную оболочку; набор доступных ключей у `ps`, `grep`, `killall` и `pidof` может зависеть от сборки.

### Найти процессы `maind`

```sh
ps | grep '[m]aind'
```

Более прямой способ, если доступен `pidof`:

```sh
pidof maind
```

### Посмотреть командную строку конкретного PID

```sh
tr '\0' ' ' < /proc/1159/cmdline
echo
```

Подставьте актуальный PID из `ps`/`pidof`; PID `1159` — только тот, который наблюдался во время одного из исследований.

### Посмотреть открытые input-узлы

Если доступен `ls`:

```sh
ls -l /proc/1159/fd 2>/dev/null | grep '/dev/input/event'
```

В BusyBox `ls -l` может показывать ссылки на узлы. При отсутствии `grep`/нужного формата смотрите каталог `/proc/<PID>/fd` напрямую.

### Условно завершить все экземпляры `maind`

```sh
if pidof maind >/dev/null 2>&1; then
    killall maind
fi
```

Это завершает **все** роли `maind`, в том числе медиапроцесс и сервисы обновления/телеметрии, если они запущены. Возможен автоматический рестарт через `quasar_launcher2`.

### Завершить только `maind --platformd`

Наиболее переносимый вариант для BusyBox — проверить `cmdline` у каждого PID:

```sh
for pid in $(pidof maind 2>/dev/null); do
    if tr '\0' ' ' < "/proc/$pid/cmdline" | grep -q -- '--platformd'; then
        kill "$pid"
    fi
done
```

Сначала лучше вывести найденные PID и командные строки без `kill`, чтобы проверить совпадение. Для принудительного завершения (`kill -9`) переходить только если обычный `kill` не сработал: это может прервать запись данных и вызвать рестарт.

## 12. Следующие шаги в Ghidra

Приоритетный список, чтобы не расходиться по вспомогательным функциям:

1. **Найти таблицу `input_event.code → logical button ID`.** Проследить записи, которые создаются в `FUN_009df930`, затем как они копируются через `FUN_009e04a2`, `FUN_009e045c`, `FUN_009e14b6`, `FUN_009e1456` и используются в `FUN_009e26b0`.
2. **Определить структуру записи размером `0x18`.** Зафиксировать offset каждого поля и все места чтения/записи; не назначать значениям `14` и `5` смысл до подтверждения.
3. **Проследить флаг `param_18 & 1` в `initButtons`.** Найти, кто задаёт этот флаг и почему выбирается `registerClickPressedAction` или `registerClickAction`.
4. **Открыть вызывающий код `FUN_009e2170` и виртуальные методы `ButtonsHandler`.** Это может помочь связать событие с зарегистрированными callback-функциями и таймингами кликов.
5. **Проверить, как именно вызывается callback для ID `0`.** Проследить путь от `FUN_009e26b0` через промежуточный resolver/handler до `startConversation` и `stopConversation`.
6. **Проследить условия блокировки** (`FUN_009fe360`, `ButtonActionLocked`, `deepStandByEnabled`) до места их установки.
7. **Сделать резервную копию бинарника и конфигурации перед патчем.** Начинать с изменения одного места и проверять diff/хэш, чтобы можно было откатиться.

### Что пока не установлено

- Какой точный Linux key code отправляет физическая кнопка активации.
- Полная схема `gpio_keypad` и `adc_keypad` с физическими кнопками и значениями событий.
- Структура и семантика всех полей записей по `0x18` байт.
- Что именно обозначают параметры `14` и `5` в записи `gpio_keypad`.
- Как устроен флаг, выбирающий между регистраторами click/click-pressed.
- Какую часть поведения создаёт локальный `maind`, а какую — последующие сервисы/облачная логика.

## 13. Практические выводы

1. Для исследования реакции физической кнопки на устройстве следует начинать с `maind --platformd`, `DevInputButtons` и таблицы соответствий input-кодов, а не с медиапроцесса или моделей распознавания речи.
2. Если требуется изменить действие кнопки, самый перспективный участок — регистрация callback для логического `ACTIVATE` (ID `0`) и обработчики `startConversation`/`stopConversation`. Низкоуровневые обёртки `std::function` вряд ли являются правильной точкой изменения.
3. Одна и та же кнопка может вести себя по-разному в зависимости от состояния устройства, длительности/типа клика, конфигурации и блокировок. Необходимо учитывать это перед выводом «кнопка не работает».
4. Перед остановкой процессов или изменением файлов прошивки нужно сохранить копии и проверить механизм автоматического перезапуска Quasar.

## 14. Словарь

- **Linux input code** — код события, который приходит от `/dev/input/event*`.
- **Logical button ID** — внутренний идентификатор кнопки в `ButtonsHandler`; например, `ACTIVATE = 0`.
- **`DevInputButtons`** — компонент, читающий Linux input-события и переводящий их в события кнопок приложения.
- **`ButtonsHandler`** — компонент, к которому привязываются действия по типу кнопки и типу нажатия.
- **Callback** — функция, зарегистрированная для вызова при событии.
- **Thumb address** — адрес ARM-функции с учётом Thumb-бита; адреса из дизассемблера могут отображаться с младшим битом `1`.
- **Quasar launcher** — механизм запуска сервисов; может перезапускать завершённые процессы.
